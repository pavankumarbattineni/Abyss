# MCP OAuth 2.1 Integration — Architecture Proposal

**Status:** Draft for review — no code has been written yet.

This document is the output of a full review of the existing MCP server integration
(`abyss_backend/routers/mcp.py` and everything it touches) and a proposed design to add
OAuth 2.1 (automatic + manual) alongside the existing `X-API-KEY`-per-connection flow.

---

## 1. Current flow — how `X-API-KEY` works today

### 1.1 Data model

`abyss_backend/database/models.py`

```python
class MCPConnection(BasicModel):        # table: mcp_connections
    user_id: str        # FK users.id, cascade delete
    name: str
    url: str
    api_key: str          # Fernet-ciphertext, NOT plaintext
    transport: str         # "streamable_http" | "sse"
    status: str            # "connected" | "disconnected" (pause/resume, independent of soft-delete)
    # + BasicModel: id (uuid str), created_at, updated_at, is_active (soft delete)

class MCPTool(BasicModel):              # table: mcp_tools
    connection_id: str    # FK mcp_connections.id, cascade delete
    name: str
    description: str | None
    permission_state: str  # "allowed" | "requires_approval" | "blocked"
    # unique (connection_id, name)

class AgentTool(BasicModel):            # table: agent_tools — junction Agent <-> MCPTool
```

There is **no migration tool** in this repo — tables are created via
`Base.metadata.create_all` at startup (`abyss_backend/main.py`). `create_all` never alters
existing tables. This matters directly for this project (see §7).

### 1.2 Encryption

`abyss_backend/utils/encryption.py` — a single app-level master secret
(`config["MCP"]["encryption_key"]`) is stretched via PBKDF2-HMAC-SHA256 into a Fernet key,
namespaced by a `purpose` string (`"mcp"` default, `"llm"` for `LlmCredential`). Only 3
call sites exist today, all narrow: encrypt on create, decrypt when actually calling out
to a server.

### 1.3 Request lifecycle

`routers/mcp.py` → `services/mcp_service.py` → `utils/mcp_client.py`:

- **Create** (`POST /mcp-connections`, JWT-only): validates reachability with the **raw
  plaintext** key first (`_validate_connection`, builds a `MultiServerMCPClient` from
  `langchain_mcp_adapters` with header `{"x-api-key": raw_key}`, calls `.get_tools()`).
  Only on success does it Fernet-encrypt the key and write the row + `MCPTool` rows in one
  transaction.
- **List** (`GET /mcp-connections`, JWT or platform `X-Api-Key`): pure DB read, no network
  call.
- **Update** (`PATCH /mcp-connections/{id}`): **name only** — url/api_key/transport are
  immutable; changing them requires delete + recreate.
- **Status toggle** (`PATCH .../status`): connect re-validates + re-syncs tools; disconnect
  just flips a flag and evicts in-memory state, keeps everything else.
- **Refresh** (`POST .../refresh`): decrypts the stored key, re-fetches the remote tool
  list, upserts `MCPTool` rows (never hard-deletes — sets `is_active=False` for tools no
  longer present).
- **Delete**: soft-delete + cascade-deactivate tools/agent-tool links + evict from
  in-memory registry + invalidate compiled LangGraph caches.

`utils/mcp_client.py::_build_server_config` is the **single place** the outbound header is
built:

```python
{"url": conn.url, "transport": conn.transport, "headers": {"x-api-key": decrypt_value(conn.api_key)}}
```

A fresh `MultiServerMCPClient` (and thus a fresh handshake) is created on every registry
rebuild/refresh/reconnect — there's no long-lived pooled session beyond process lifetime.

**Important naming collision to keep straight:** the platform's own API key
(`sk-tl-...`, table `ApiKey`, used to authenticate *callers of the Abyss REST API*) is a
completely different thing from `MCPConnection.api_key` (used to authenticate *Abyss to a
downstream MCP server*). OAuth only replaces the latter.

### 1.4 Frontend

- `abyss_frontend/src/components/pages/mcp/mcp.tsx` — table of connections
  (`GET /mcp-connections` via react-query), row click opens `ConnectorToolsDialog`.
- `add-server-dialog.tsx` — RHF + Zod form: `name`, `url`, `api_key` (password input),
  transport hardcoded to `"streamable_http"`. `POST /mcp-connections`.
- `edit-server-dialog.tsx` — name-only form, matching backend's PATCH constraint.
- `connection-actions.tsx` — row menu: view tools / refresh / connect-disconnect / edit /
  delete. The delete-via-tools-dialog button is currently dead code (`disabled`
  hardcoded) — a natural place for a future "revoke" action.
- `connector-tools-dialog.tsx` — per-tool 3-way permission toggle + bulk-set.
- `services/mcp-service.ts` — thin axios wrapper, one method per endpoint.
- `types/mcp.ts` — mirrors `schemas/mcp.py`.
- Frontend's shared `axios.ts` attaches the user's own JWT to every call — **no MCP
  connection secret ever appears in the frontend today**, and per `abyss_frontend/CLAUDE.md`
  §12 ("no secrets in the frontend"), that must stay true for OAuth client secrets too.
- `abyss_frontend/CLAUDE.md` already sketches a `ToolAuthType = "oauth" | "key"` concept
  and an "OAuth tools show a connect flow with a progress state" pattern in its design
  notes — this work is the first place that gets implemented.

There is **no existing OAuth 2.1/PKCE/DCR code anywhere in the repo**. `services/oauth_service.py`
and `routers/auth.py` only handle Abyss's own login (Firebase ID token → Abyss JWT pair) —
useful as a rough shape ("redirect out, exchange something for a token, store it") but not
reusable machinery.

## 2. Design decisions (confirmed with you)

1. **Automatic flow = full MCP-spec discovery + Dynamic Client Registration.** Abyss
   fetches the server's OAuth metadata and self-registers a client (RFC 7591) — the user
   supplies nothing but the MCP server URL and clicks "Connect." Falls back to the manual
   flow if the server doesn't support discovery/DCR.
2. **Manual flow = full manual endpoint entry.** When a server has no discoverable
   metadata, the user supplies `authorization_url`, `token_url`, `client_id`,
   `client_secret` (optional), and `scope` directly.
3. **Alembic is being introduced** as part of this work, replacing bare `create_all` for
   schema changes going forward. First migration: a baseline capturing current schema,
   second: the new OAuth columns/tables.

## 3. Proposed data model

Extend `MCPConnection` with a discriminator and make `api_key` nullable; add a child table
for OAuth state so a connection can hold multiple grants over its lifetime (e.g. after
reauthorization) without losing history, and so we're not cramming unrelated attributes
onto the parent row.

```python
class MCPConnection(BasicModel):                 # table: mcp_connections
    user_id: str
    name: str
    url: str
    transport: str
    status: str
    auth_type: str = "api_key"    # NEW: "api_key" | "oauth"   (default preserves existing rows)
    api_key: str | None            # NEW: now nullable — only used when auth_type == "api_key"
    oauth_grant: relationship("MCPOAuthGrant", uselist=False, cascade="all, delete-orphan")


class MCPOAuthGrant(BasicModel):                  # table: mcp_oauth_grants  (NEW)
    connection_id: str          # FK mcp_connections.id, unique, cascade delete
    mode: str                    # "automatic" | "manual"
    # Client identity (from DCR response, or user-entered for manual)
    client_id: str
    client_secret_encrypted: str | None   # Fernet, purpose="mcp_oauth" — None for public/PKCE-only clients
    # Discovered/entered endpoints (persisted so refresh doesn't require re-discovery)
    authorization_endpoint: str
    token_endpoint: str
    registration_endpoint: str | None
    scope: str | None
    # Token material — all Fernet-encrypted, purpose="mcp_oauth"
    access_token_encrypted: str | None
    refresh_token_encrypted: str | None
    token_expires_at: datetime | None
    # Status
    status: str = "pending"     # "pending" | "active" | "expired" | "revoked" | "error"
    last_error: str | None       # human-readable reason, surfaced to the UI
```

Why a child table instead of columns on `MCPConnection`:
- Keeps `MCPConnection` meaningful for both auth types without a wide sparse row.
- A unique `connection_id` FK today, but structurally allows re-authorization to overwrite
  in place while keeping the door open for audit/history later without another migration.
- Matches the existing separation-of-concerns precedent (`LlmCredential` is already its own
  table, not columns on whatever it's attached to).

Ephemeral PKCE/state (`code_verifier`, `state`, `nonce`, which connection/user initiated
it) is **not** persisted to Postgres — it's short-lived (minutes) and only needed to
validate the callback. Store it server-side keyed by `state` with a short TTL. Given no
Redis/cache layer currently exists in this backend (needs confirming — see open question
in §9), the pragmatic default is a small `mcp_oauth_pending` table with a `created_at` +
cleanup-on-read, or an in-process TTL dict guarded the same way `utils/mcp_client.py`
already keeps in-memory registries (acceptable since a single backend process today, but
won't survive multi-worker/horizontal scaling — flagged as an explicit tradeoff to confirm).

## 4. Backend flow design

### 4.1 Automatic flow (discovery + DCR)

Per the MCP authorization spec (which itself layers on OAuth 2.1 + RFC 9728 + RFC 8414 +
RFC 7591):

1. **User action:** clicks "Connect with OAuth" in `AddServerDialog`, having entered only
   `name` + `url` (+ optional `scope` hint).
2. `POST /mcp-connections/oauth/discover` `{ url }` — backend:
   - Tries `GET {url}/.well-known/oauth-protected-resource` (RFC 9728) to find the
     `authorization_servers` list; falls back to treating `url`'s origin as the
     authorization server directly if that 404s (older/simpler servers).
   - `GET {authorization_server}/.well-known/oauth-authorization-server` (RFC 8414) to get
     `authorization_endpoint`, `token_endpoint`, `registration_endpoint`,
     `scopes_supported`.
   - If `registration_endpoint` present: `POST` a Dynamic Client Registration request
     (RFC 7591) with Abyss's fixed `redirect_uris: [f"{BACKEND_PUBLIC_URL}/api/v1/mcp-connections/oauth/callback"]`,
     `token_endpoint_auth_method: "none"` (PKCE, public client) unless the server requires
     a confidential client. Persists the returned `client_id`/`client_secret` immediately
     (encrypted) against a **pending, not-yet-connected** `MCPConnection` +
     `MCPOAuthGrant(status="pending")`.
   - Returns `{ connection_id, supports_automatic: bool, discovered: {...} }` to the
     frontend. If discovery/DCR fails at any step, returns `supports_automatic: false` and
     the frontend falls back to the manual form (no dead end for the user).
3. **Frontend:** on `supports_automatic: true`, immediately calls
   `POST /mcp-connections/{id}/oauth/authorize` (or the discover step returns the URL
   directly) which the backend builds as:
   - Generates PKCE `code_verifier`/`code_challenge` (S256) and a random `state`, stores
     them server-side keyed by `state` (TTL ~10 min), associated with `connection_id` +
     `user_id` (ownership check on callback).
   - Returns `{ authorization_url }` — full URL with `client_id`, `redirect_uri`,
     `response_type=code`, `code_challenge`, `code_challenge_method=S256`, `scope`,
     `state`.
   - Frontend opens this in a popup (`window.open`) rather than a full navigation, so the
     SPA state isn't lost.
4. **User authorizes** at the MCP server's own login/consent screen.
5. **Provider redirects** to `GET /api/v1/mcp-connections/oauth/callback?code=...&state=...`
   (backend route, not frontend — the code exchange needs the client secret, which must
   never reach the browser):
   - Looks up pending state by `state`; 400 if missing/expired/mismatched (CSRF
     protection).
   - Exchanges `code` + `code_verifier` at `token_endpoint` for
     `{access_token, refresh_token?, expires_in, scope}`.
   - Validates reachability the same way the existing API-key flow does — one live
     `.get_tools()` call via `MultiServerMCPClient` with an `Authorization: Bearer` header
     — before marking anything "connected," matching existing create-flow behavior of
     "prove it works before committing."
   - Encrypts + stores tokens, flips `MCPOAuthGrant.status = "active"`,
     `MCPConnection.status = "connected"`, persists `MCPTool` rows exactly like today's
     `_persist_synced_tools`.
   - Returns a small HTML page that `postMessage`s success/failure to the opener window
     and closes itself (standard OAuth-popup pattern) — the opener's message handler
     invalidates the `["mcp-connections"]` react-query key and closes the dialog.
6. **On denial/error** at the provider, or discovery/DCR/token-exchange failure: the
   popup shows a short error page (postMessage failure + reason), connection row (if one
   was speculatively created at discover-time) is deleted rather than left in a stuck
   "pending" state — no orphaned partial connections.

### 4.2 Manual flow

1. User picks "Manual OAuth configuration" in `AddServerDialog`, fills in:
   `name`, `url`, `authorization_url`, `token_url`, `client_id`, `client_secret`
   (optional), `scope`.
2. `POST /mcp-connections/oauth/manual` — backend validates the URLs are well-formed
   HTTPS (except localhost in dev), creates `MCPConnection(auth_type="oauth")` +
   `MCPOAuthGrant(mode="manual", status="pending", ...)` with the given endpoints/client
   (secret encrypted immediately if present).
3. From here the flow is **identical to steps 3–6 of §4.1** — same
   `/oauth/authorize` → provider → `/oauth/callback` path, just skipping the discovery/DCR
   step because the endpoints/client are already on the row. This is the main reason to
   share one `MCPOAuthGrant` shape and one authorize/callback implementation for both
   modes rather than forking the code path.

### 4.3 Token refresh

- `utils/mcp_client.py::_build_server_config` gets a new branch:
  ```python
  if conn.auth_type == "oauth":
      token = get_valid_access_token(conn.oauth_grant)   # refreshes if expiring within e.g. 60s
      headers = {"Authorization": f"Bearer {token}"}
  else:
      headers = {"x-api-key": decrypt_value(conn.api_key)}
  ```
- `get_valid_access_token`: if `token_expires_at` is within a short buffer of now (or
  already past), POST to `token_endpoint` with `grant_type=refresh_token`; on success,
  re-encrypt + persist new access/refresh token + expiry (refresh tokens may rotate — some
  servers issue a new refresh token every use, so always overwrite, not just append).
  On failure (400 `invalid_grant` = revoked/expired refresh token), set
  `MCPOAuthGrant.status = "expired"`, `MCPConnection.status = "disconnected"`,
  `last_error = "Reauthorization required"`, and raise — caller (registry build /
  refresh endpoint / agent invocation) surfaces this the same way a validation failure is
  surfaced today (422 for interactive calls; the connection is simply skipped in the
  startup registry build with a logged warning, matching current unreachable-server
  behavior).
- Also handle **reactive** refresh: if a live call to the MCP server still 401s despite a
  fresh-looking token (server-side revocation between our expiry check and the call),
  refresh once and retry once; if that also fails, same "expired" handling as above.
- This refresh path is called both lazily (right before use, in `_build_server_config`)
  and can be invoked directly via a new `POST /mcp-connections/{id}/oauth/refresh` for the
  frontend to proactively check/repair status without a full reconnect.

### 4.4 Reconnect / revoke / disconnect

- **Disconnect** (existing `PATCH .../status`): unchanged behavior for `oauth` connections
  too — just flips `status`, doesn't touch tokens. Reconnecting later reuses the stored
  refresh token if still valid.
- **Revoke** (new): explicit user action, separate from disconnect. `POST
  /mcp-connections/{id}/oauth/revoke` — best-effort calls the provider's
  `revocation_endpoint` (RFC 7009) if advertised in discovery, then clears the stored
  tokens and sets `status = "revoked"`. This is what should replace the currently-dead
  "Disconnect" button in `connector-tools-dialog.tsx`, or sit alongside it — see frontend
  UX in §5.
- **Reauthorize** (new): for a connection whose grant is `expired`/`revoked`/`error`, a
  "Reconnect" action re-runs the authorize step (§4.1 step 3 onward) against the *existing*
  `MCPOAuthGrant` row (same client_id, re-discovered or manual endpoints untouched),
  replacing tokens on success. No need to redo discovery/DCR for `automatic` connections
  unless the stored `registration_endpoint`/`client_id` itself is now invalid (rare;
  handle by falling back to a fresh discover-and-register on a 400/`invalid_client` from
  the token endpoint).
- **Delete**: unchanged cascade behavior, extended so deleting an `oauth` connection also
  best-effort calls the revocation endpoint before the row (and its `MCPOAuthGrant`,
  `cascade="all, delete-orphan"`) is removed.

## 6. Security considerations

- **PKCE (S256) is mandatory** on every authorization-code exchange, automatic or manual,
  confidential or public client — this is the actual "2.1" requirement (OAuth 2.1 drops
  bare authorization-code without PKCE entirely), and protects even confidential clients
  against code-interception.
- **`state` is single-use, TTL-bound, and bound to the requesting user** — callback must
  verify the authenticated session matches the user who initiated the flow, not just that
  `state` matches, to prevent one user's callback being replayed onto another's session.
- **Client secrets and tokens never reach the frontend.** All exchange/refresh happens
  backend-to-provider; the frontend only ever receives connection metadata + status.
- **Redirect URI is a fixed, backend-owned, non-configurable value** — never accept a
  caller-supplied `redirect_uri`; always use `f"{BACKEND_PUBLIC_URL}{API_V1_PREFIX}/mcp-connections/oauth/callback"`
  from server config, to prevent open-redirect/token-leak via a manipulated redirect.
- **Encrypt access token, refresh token, and client_secret at rest**, reusing
  `utils/encryption.py` with a new `purpose="mcp_oauth"` (keeps key derivation separate
  from the existing `"mcp"`/`"llm"` purposes, same pattern, no new crypto code needed).
- **Authorization/token/registration endpoints must be HTTPS** (except explicit localhost
  for local dev MCP servers) — reject `http://` discovery results in non-dev environments.
- **DCR requests should not blindly trust arbitrary `registration_endpoint`** values —
  only follow one that came from the same server's own metadata response, not a
  user-suppliable field, to avoid SSRF-style abuse via the discovery step (discovery/DCR
  calls happen from the backend, so URL validation on `url`/discovered endpoints matters —
  reject non-http(s) schemes, reject private/link-local IP targets unless dev mode, same
  caution already implicitly needed for the existing "connect to an arbitrary user-supplied
  MCP URL" feature, just extended to the two new discovery calls).
- **Ownership check on every OAuth-scoped endpoint** — `connection_id` must belong to
  `current_user.id`, same as every other mutating MCP endpoint today.
- **Least-scope by default** — if the discovery response lists `scopes_supported` and the
  user didn't narrow it, request the minimal scope the MCP server's metadata suggests
  rather than requesting everything.

## 7. Database migration plan (Alembic introduction)

1. Add `alembic` to backend dependencies, `alembic init`, point `env.py` at the existing
   `Base.metadata` / async engine config from `database/`.
2. **Migration 0001 (baseline):** `alembic revision --autogenerate` against the current
   schema, review the diff carefully (it should be a no-op against a DB already created by
   `create_all` — this is purely to give Alembic a starting point matching today's schema),
   commit it.
3. **Migration 0002 (this feature):**
   - `ALTER TABLE mcp_connections ADD COLUMN auth_type VARCHAR(20) NOT NULL DEFAULT 'api_key'`
   - `ALTER TABLE mcp_connections ALTER COLUMN api_key DROP NOT NULL`
   - `CREATE TABLE mcp_oauth_grants (...)` per §3, with FK + unique on `connection_id`.
   - Backfill: none needed — existing rows get `auth_type='api_key'` via the column
     default, no `MCPOAuthGrant` row, which is exactly correct (they're api_key
     connections).
4. Replace the `Base.metadata.create_all(...)` startup call in `main.py` with an Alembic
   `upgrade head` step (or document it as a required deploy step) — needs a decision on
   whether to run it automatically at startup or as an explicit ops step; recommend
   explicit (safer, avoids surprise schema changes on pod restart) but flagging as an open
   question for you.

## 8. Backward compatibility

- Every existing endpoint keeps its current request/response shape for `auth_type='api_key'`
  connections — `MCPConnectionCreate` becomes a discriminated shape (`auth_type` field,
  default `"api_key"`, existing `{name, url, api_key, transport}` payload still works
  unchanged when omitted or set to `"api_key"`).
- `_build_server_config`/`_validate_connection`/`_fetch_remote_tools` branch on
  `auth_type`; the existing `x-api-key` path is untouched code, not rewritten.
- Frontend's existing "API Key" tab in `AddServerDialog` is pixel-identical to today's
  form — OAuth is strictly additive UI.
- No changes to `MCPTool`, `AgentTool`, permissions, or any agent-execution code — OAuth
  only changes *how a connection authenticates*, nothing downstream of a successful
  `.get_tools()` call.

## 9. Open questions before finalizing the implementation plan

1. **State/PKCE storage:** in-process TTL dict (simple, breaks under multi-worker/horizontal
   scaling) vs. a new lightweight `mcp_oauth_pending` DB table (works everywhere, slightly
   more code) vs. introducing Redis (bigger infra change). Given this backend appears to
   run as a single process today but likely won't stay that way — do you want the DB-table
   option now, or is in-process acceptable for a first cut?
2. **`BACKEND_PUBLIC_URL` config:** there's currently no backend-facing "my own public URL"
   setting (only `NEXT_PUBLIC_API_URL` on the frontend side, pointing *at* the backend).
   The OAuth `redirect_uri` needs one. Should this be a new `THINKLOOP_CONFIG.MCP.backend_public_url`
   entry, or is there an existing env var/reverse-proxy convention I should use instead?
3. **Library choice:** recommend `authlib` (`AsyncOAuth2Client`) for the PKCE
   authorize-URL/token-exchange/refresh mechanics, with plain `httpx` (already a
   dependency) for the two discovery GETs and the DCR POST. Fine to add `authlib`, or do
   you want this hand-rolled with `httpx` only to avoid a new dependency?
4. **Popup vs. full-page redirect** for the frontend authorize step — assumed popup +
   `postMessage` (keeps the dashboard SPA state intact, standard pattern). Confirm that's
   preferred over a full-page redirect-away-and-back.
5. Where the dead "Disconnect" button in `connector-tools-dialog.tsx` should go once Revoke
   exists (remove it vs. repurpose it) — noted in §5, not blocking, just needs a call.

## 10. Suggested implementation phases (high level)

Once the above is confirmed, this becomes a formal task-by-task plan (per
`superpowers:writing-plans`). Proposed phase breakdown:

1. **Alembic bootstrap** — baseline migration, replace `create_all` call, no behavior
   change.
2. **Schema** — `auth_type` column, nullable `api_key`, `mcp_oauth_grants` table + model +
   migration.
3. **Encryption/config plumbing** — new `purpose="mcp_oauth"`, `BACKEND_PUBLIC_URL` config.
4. **Backend: manual flow** (simpler, no discovery/DCR) — `/oauth/manual`,
   `/oauth/authorize`, `/oauth/callback`, `_build_server_config` Bearer-header branch,
   refresh logic. Fully working end-to-end for one flow before adding discovery.
5. **Backend: automatic flow** — `/oauth/discover` (RFC 9728 + 8414 + 7591), reusing the
   authorize/callback/refresh machinery from phase 4.
6. **Backend: lifecycle endpoints** — revoke, reconnect, status surfacing on
   `MCPConnectionResponse`.
7. **Frontend: manual flow UI** — auth-type toggle, manual OAuth form, popup +
   `postMessage` handling, status badge update.
8. **Frontend: automatic flow UI** — "Connect with OAuth" one-click path, discovery
   fallback wiring into the manual form.
9. **Frontend: lifecycle UI** — reconnect/revoke actions, expired-state messaging.
10. **End-to-end verification** — test against at least one real MCP server with full
    discovery/DCR support and one requiring manual configuration, plus the existing
    api_key regression path.
