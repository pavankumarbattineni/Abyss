1. TOOL APPROVAL WORKFLOW
================================================================

OVERVIEW
--------
The tool approval workflow governs how MCP (Model Context Protocol) tools are executed, with a permission system that controls whether tools run automatically, require user approval, or are blocked entirely. This system ensures security and user control over external tool execution while maintaining a smooth user experience.

PERMISSION STATES
-----------------
Each MCPTool has a permission_state field with three possible values:

- "allowed": Tool runs automatically without any user intervention
- "requires_approval": Tool pauses execution and waits for explicit user approval before running
- "blocked": Tool is completely unavailable to all agents, regardless of assignment

Permission states are global per tool - when a tool's permission changes, it affects every agent that uses that tool. This is enforced at the database level (MCPTool.permission_state) and reflected in the in-memory tool registry.

TOOL ASSIGNMENT TO AGENTS
---------------------------
Tools are assigned to agents through the AgentTool junction table:
- AgentTool.agent_id → which agent can use the tool
- AgentTool.tool_id → which MCP tool is assigned
- Both agent and tool must be active (is_active=True)

An agent can have multiple tools assigned, and a tool can be assigned to multiple agents. The assignment is independent of permission state - a tool can be assigned to an agent even if it's blocked (it simply won't be offered to the LLM).

PERMISSION EVALUATION BEFORE EXECUTION
---------------------------------------
When an agent (parent or sub-agent) attempts to execute tools:

1. The graph's "tools" node (make_tools_node in graph_builder.py) receives the tool_calls from the LLM's AIMessage
2. It checks each tool call against the permissions map: {tool_name: requires_approval}
3. Tools marked as requiring approval are collected into a "gated" list
4. The execution context is checked: is_interactive flag determines behavior

INTERACTIVE VS UNATTENDED RUNS
-------------------------------
The is_interactive flag is set at graph invocation time:
- True: Normal chat messages where a user is present to approve
- False: Scheduled runs and other unattended executions

For unattended runs (is_interactive=False):
- Gated tools are automatically denied without pausing
- The agent receives a denial message explaining the tool was skipped due to lack of approval availability
- This prevents scheduled runs from hanging indefinitely waiting for approval

For interactive runs (is_interactive=True):
- Gated tools trigger an interrupt() call in the graph
- Execution pauses and waits for user decision
- StreamRecord.status changes to AWAITING_APPROVAL

INTERRUPT MECHANISM
-------------------
When tools require approval in interactive mode:

1. The tools_node calls interrupt() with a payload containing:
   - reason: The agent's reasoning for wanting to use the tool(s)
   - agent_id: The agent attempting to use the tools (for "Always Allow" resolution)
   - tool_calls: Array of gated tool calls with:
     - tool_call_id: LangGraph's identifier for this specific call
     - tool_name: Human-readable tool name
     - tool_id: Database primary key (for permission updates)
     - args: Serialized tool arguments

2. LangGraph's checkpointer persists this interrupt in the thread's checkpoint
3. The astream_events loop in _run_generation stops yielding events
4. The checkpoint is queried for pending interrupts after the loop ends
5. If interrupts exist, the stream status is set to AWAITING_APPROVAL
6. The interrupt payload is sent to the client via SSE as a tool_approval_required event

PENDING APPROVAL STATE
----------------------
While waiting for approval:
- StreamRecord.status = AWAITING_APPROVAL
- StreamRecord.partial_content contains all content generated before the pause
- StreamRecord.reasoning contains all reasoning steps before the pause
- Token usage (input_tokens, output_tokens, cache_read_tokens) is persisted
- The graph's checkpoint holds the exact interrupt state
- In-memory SSE buffer remains alive for reconnection
- No cleanup timer is scheduled (unlike terminal states)

The interrupt is durable - if the server restarts or the in-memory buffer is cleaned up, the pending approval can still be recovered from the checkpoint via get_pending_approval().

USER APPROVAL OPTIONS
---------------------
The user can respond with three types of decisions per tool call:

1. "allow_once": Run the tool this one time only
   - Tool executes immediately
   - Permission state remains "requires_approval"
   - Future calls will again require approval

2. "always_allow": Run the tool and permanently change permission
   - Tool executes immediately
   - MCPTool.permission_state is updated to "allowed" in the database
   - In-memory tool registry is updated for all affected agents
   - Compiled graph cache is invalidated for all agents using this tool
   - Future calls run automatically without approval

3. "deny": Skip the tool call
   - Tool does not execute
   - Agent receives a denial message explaining the user declined
   - Agent continues with whatever else it can do
   - Permission state remains unchanged

APPROVAL RESOLUTION PROCESS
---------------------------
When the user submits approval decisions (POST /streams/{stream_id}/tool-approvals):

1. Atomic claim: StreamRecord status is atomically changed from AWAITING_APPROVAL to RUNNING
   - WHERE status=AWAITING_APPROVAL ensures only one claim succeeds
   - Prevents duplicate submissions from racing

2. Interrupt validation: The actual pending interrupts are loaded from the graph's checkpoint
   - Client-provided interrupt_ids are validated against checkpoint state
   - Prevents forged or stale approval requests

3. Decision mapping: For each interrupt, tool_call_id → decision is built
   - "allow_once" and "always_allow" both map to "allow" for the resume
   - "always_allow" additionally triggers permission state updates

4. Permission updates (if "always_allow" was chosen):
   - MCPTool.permission_state is set to "allowed" in the database
   - set_tool_permission_in_registry() updates the in-memory registry
   - invalidate_graph_cache() busts compiled graphs for affected agents
   - Parent agents of sub-agents are also invalidated

5. Graph resumption: A new _run_generation task is created with:
   - resume_map: {interrupt_id: {tool_call_id: "allow"|"deny"}}
   - starting_chunk_index: Continues chunk numbering from where it paused
   - user_message: Empty string (ignored on resume)

6. The graph receives Command(resume=resume_map) instead of a new message
   - LangGraph replays the tools_node with the decisions
   - Allowed tools execute, denied tools are skipped
   - Execution continues normally from that point

RESUME BEHAVIOR
---------------
When execution resumes after approval:
- The graph replays the tools_node with the pre-approved decisions
- No additional LLM call is made for the same decision point
- Previously generated content and reasoning are preserved
- Token usage accumulates across the pause boundary
- Chunk numbering continues seamlessly
- The user sees no interruption in the stream

The resume_map is keyed by interrupt_id, allowing multiple simultaneous interrupts (e.g., parallel sub-agent branches each needing approval) to be resolved in one API call.

CANCELLATION WHILE AWAITING APPROVAL
-------------------------------------
If the user cancels (DELETE /streams/{stream_id}) while status is AWAITING_APPROVAL:
- deny_all_pending_approvals() is called
- All pending tool calls are denied
- The graph is resumed with all decisions set to "deny"
- The agent's natural follow-up generation runs in the background
- The client can reconnect to see the agent's response to the denial

This is necessary because leaving the interrupt dangling would break the thread - future messages would replay the stale pending tool call instead of processing new input.

SCHEDULED-AGENT BEHAVIOR WITH GATED TOOLS
------------------------------------------
Scheduled runs (is_interactive=False) handle gated tools differently:
- The tools_node checks is_interactive before calling interrupt()
- If is_interactive=False and tools are gated, they are auto-denied
- No interrupt is raised, no pause occurs
- The agent receives a message: "Skipped {tool_name}: it requires approval and this agent ran unattended"
- Execution continues immediately
- This prevents scheduled runs from hanging indefinitely

This means tools that work fine with approval in interactive mode may be effectively unavailable in scheduled runs unless set to "allowed".

PERMISSION STATE TRANSITIONS
----------------------------
When permission_state changes:

1. "allowed" → "requires_approval":
   - In-memory registry updated: permissions[tool_name] = True
   - Graph cache invalidated for affected agents
   - Future executions will pause for approval

2. "requires_approval" → "allowed":
   - In-memory registry updated: permissions[tool_name] = False
   - Graph cache invalidated for affected agents
   - Future executions run automatically

3. "requires_approval" → "blocked":
   - Tool is removed from all agent registries entirely
   - Graph cache invalidated for affected agents
   - Tool is never offered to the LLM again

4. "blocked" → "requires_approval" or "allowed":
   - NOT handled by set_tool_permission_in_registry()
   - Requires a connection refresh (POST /mcp-connections/{id}/refresh)
   - The tool was dropped from the registry and must be re-fetched

EDGE CASES AND FAILURE SCENARIOS
----------------------------------
1. **Concurrent approval submissions**: Atomic WHERE status=AWAITING_APPROVAL claim prevents racing

2. **Stale approval requests**: Interrupt IDs are validated against the actual checkpoint state

3. **Forged tool_call_ids**: The server uses checkpoint state, not client-provided data

4. **Server restart during approval**: Checkpoint is durable; pending approval can be recovered

5. **Tool execution failure after approval**: Tool errors are caught and returned as error messages to the agent

6. **Multiple tools requiring approval**: All are grouped in one interrupt for batch approval

7. **Parallel sub-agents with approvals**: Each sub-agent's interrupt is independent; resume_map handles multiple

8. **Agent deleted while awaiting approval**: Ownership check in _load_pending_interrupts will fail

9. **Tool deleted while awaiting approval**: The interrupt payload still has tool_id for resolution

10. **Always Allow on non-existent tool**: Database update will fail; transaction rolls back

SECURITY CONSIDERATIONS
-----------------------
- Interrupt payloads include the real database tool_id, not just names (names are only unique per connection)
- Client-provided data is never trusted for permission decisions
- "Always Allow" requires database write and cache invalidation, not just in-memory change
- Permission changes are global per tool, affecting all agents immediately
- Ownership is verified via thread → user_id before allowing any approval resolution

2. PROVIDER KEYS / BYOK (BRING YOUR OWN KEY) WORKFLOW
================================================================

OVERVIEW
--------
ThinkLoop supports two modes of LLM provider key management:
1. Platform-provided keys (default): The platform's own API keys for supported providers
2. User-provided keys (BYOK): Users bring their own API keys for specific providers

This workflow explains how keys are configured, stored, selected, validated, and used during agent execution.

PROVIDER AND MODEL CATALOG
---------------------------
The database maintains a catalog of supported providers and models:

Provider table:
- id: Unique identifier
- name: Provider name (e.g., "openai", "anthropic", "google")
- display_name: Human-readable name

ProviderModel table:
- id: Unique identifier
- provider_id: Foreign key to Provider
- model_name: Technical model name (e.g., "gpt-4o", "claude-3-5-sonnet-20241022")
- display_name: Human-readable model name
- is_platform_default: Boolean flag (only one row can be true across entire table)

The platform default model is the one used when an agent has llm_model_id=NULL. This allows the platform to change the default model without migrating agent rows.

USER CREDENTIAL STORAGE
-----------------------
User-provided keys are stored in the LlmCredential table:
- id: Unique identifier
- user_id: Foreign key to User
- provider_id: Foreign key to Provider
- encrypted_api_key: Fernet-encrypted API key (purpose="llm")
- is_active: Soft-delete flag

Encryption:
- Keys are encrypted using Fernet symmetric encryption
- Encryption purpose is "llm" to separate from other encrypted fields
- The encryption key is configured in the environment
- Keys are never stored in plaintext
- Decryption happens only at runtime when building the LLM instance

Unique constraint: (user_id, provider_id) ensures one key per provider per user.

KEY VALIDATION
--------------
Before storing a user's API key, it is validated against the provider:

OpenAI validation (llm_providers.py):
- Calls OpenAI().models.list() with the provided key
- Raises ValueError on AuthenticationError
- Raises ValueError on any other exception

Anthropic validation:
- Calls Anthropic().models.list() with the provided key
- Raises ValueError on AuthenticationError
- Raises ValueError on any other exception

Google Gemini validation:
- Calls genai.Client(api_key).models.list()
- Raises ValueError on 401/403 status codes
- Raises ValueError on any other exception

Validation happens in the upsert_credential method before any database write, ensuring invalid keys are never persisted.

KEY UPSERT PROCESS
------------------
When a user adds or updates a provider key:

1. Provider is validated as active
2. Provider spec is retrieved from PROVIDERS registry
3. API key is validated against the provider (network call)
4. If validation fails, ValueError is raised with clear message
5. If validation succeeds:
   - Existing LlmCredential row is updated OR new row is inserted
   - encrypted_api_key is set using encrypt_value()
   - is_active is set to True
6. Graph cache is invalidated for all agents using this provider
   - _invalidate_agents_for_provider() queries all agents with llm_model_id pointing to this provider
   - invalidate_graph_cache() is called for each affected agent
   - This ensures the new key is used on the next message

KEY DELETION PROCESS
--------------------
When a user deletes a provider key:

1. Provider is validated as active
2. Existing LlmCredential row is found (must be active)
3. is_active is set to False (soft delete)
4. Graph cache is invalidated for all agents using this provider
5. Agents using this provider will fail on next execution with "No {provider} API key configured"

MODEL SELECTION FOR AGENTS
---------------------------
Each Agent has an optional llm_model_id field:
- NULL: Use platform default (is_platform_default=true ProviderModel)
- Non-NULL: Use specific ProviderModel

When an agent is created or edited:
- llm_model_id can be set to a specific ProviderModel.id
- Or left NULL to use the platform default
- The UI shows "Default" as a synthetic option alongside actual provider models

LLM RESOLUTION AT RUNTIME
--------------------------
When an agent executes (resolve_llm_for_agent in chat_service.py):

Case 1: Agent.llm_model_id is NULL (platform default)
1. Query ProviderModel where is_platform_default=true and is_active=true
2. If found, use that provider/model
3. If not found, fall back to config["LLM"]["openai_model"]
4. Build LLM instance using platform's API key from config
5. Return LlmResolution with llm_source="default"

Case 2: Agent.llm_model_id is set (BYOK or explicit platform model)
1. Query ProviderModel by id, verify is_active=true
2. If not found, raise "This agent's selected model is no longer available"
3. Query LlmCredential where user_id=agent.user_id and provider_id=model.provider_id
4. If credential not found, raise "No {provider} API key configured — add one in Settings"
5. Decrypt the encrypted_api_key
6. Build LLM instance using the decrypted key
7. Return LlmResolution with llm_source="byok"

Important: There is NO platform fallback for BYOK selections. If the user's credential is missing, the execution fails immediately with a clear error message.

LLM INSTANCE CONSTRUCTION
-------------------------
LLM instances are built using the PROVIDERS registry (llm_providers.py):

PROVIDERS = {
    "openai": ProviderSpec(
        display_name="OpenAI",
        build=lambda model, api_key: ChatOpenAI(model=model, api_key=api_key),
        validate=_validate_openai_key,
    ),
    "anthropic": ProviderSpec(
        display_name="Anthropic",
        build=lambda model, api_key: ChatAnthropic(model=model, api_key=api_key),
        validate=_validate_anthropic_key,
    ),
    "google": ProviderSpec(
        display_name="Google Gemini",
        build=lambda model, api_key: ChatGoogleGenerativeAI(model=model, google_api_key=api_key),
        validate=_validate_google_key,
    ),
}

The build() function creates the appropriate LangChain chat model instance with the provided model name and API key.

SHARED PLATFORM LLM INSTANCE
----------------------------
For platform-default usage, a shared ChatOpenAI instance is reused:
- _get_llm() in chat_service.py maintains a global _llm variable
- Created on first call with configured openai_model and openai_api_key
- Configured with max_retries=2 for transient connection errors
- Uses httpx.AsyncClient with connection pooling and keepalive management
- This shared instance is used for thread title generation and platform-default agents

BYOK LLM INSTANCES
------------------
For BYOK usage, a new LLM instance is created per agent execution:
- Built fresh in resolve_llm_for_agent() using the decrypted key
- Not cached across executions (key could rotate)
- Each agent execution gets its own instance
- The instance is passed to build_agent_graph() and embedded in the compiled graph

GRAPH CACHE KEYING
------------------
Compiled graphs are cached with key (agent_id, llm_model_id or "default"):
- If llm_model_id is NULL, cache key is (agent_id, "default")
- If llm_model_id is set, cache key is (agent_id, llm_model_id)
- This means changing an agent's model selection naturally busts the cache
- Key rotation (updating LlmCredential) also busts the cache via _invalidate_agents_for_provider()

ERROR CLASSIFICATION
-------------------
During execution, provider SDK exceptions are classified (classify_llm_error in llm_providers.py):

OpenAI errors:
- AuthenticationError → "invalid_api_key"
- PermissionDeniedError → "permission_denied"
- RateLimitError → "rate_limited"

Anthropic errors:
- AuthenticationError → "invalid_api_key"
- PermissionDeniedError → "permission_denied"
- RateLimitError → "rate_limited"

Google Gemini errors:
- ClientError with 401/403 → "invalid_api_key"
- ClientError with 429 → "rate_limited"
- ServerError → "provider_unavailable"

Classified errors are surfaced to the user with clear, actionable messages instead of raw exception dumps.

SECURITY CONSIDERATIONS
------------------------
- API keys are encrypted at rest using Fernet
- Encryption purpose separates LLM keys from other encrypted fields
- Keys are never logged or exposed in error messages
- Masked keys (first 4 + last 4 characters) are shown in the UI
- Validation happens before storage to prevent invalid keys in the database
- No platform fallback for BYOK - explicit user consent required
- Graph cache is invalidated on key rotation to ensure new keys are used

FAILURE SCENARIOS
------------------
1. **Invalid API key during validation**: Clear error message, key not stored
2. **Provider unreachable during validation**: Generic error, key not stored
3. **Key rotation**: Old cached graphs invalidated, new key used on next execution
4. **Key deleted**: Agents using that provider fail with clear message
5. **Provider model deleted**: Agents using that model fail with "no longer available"
6. **Platform default model changed**: Agents with NULL llm_model_id automatically use new default
7. **Expired API key**: Provider will return authentication error during execution
8. **Rate-limited API key**: Classified error surfaced to user with retry guidance
9. **Insufficient permissions**: Classified error surfaced to user
10. **Provider outage**: Generic error or provider_unavailable classification

3. USAGE AND COST TRACKING WORKFLOW
================================================================

OVERVIEW
--------
ThinkLoop tracks token usage and calculated costs for every agent run, distinguishing between platform-provided model usage (default) and user-provided key usage (BYOK). This enables users to understand their consumption and costs across all agent executions.

USAGE CAPTURE POINTS
--------------------
Token usage is captured during the graph execution stream in _run_generation (chat_service.py):

1. For each LLM call (parent agent, sub-agents, synthesizer):
   - on_chat_model_end event fires
   - usage_metadata is extracted from the AIMessage
   - input_tokens, output_tokens, and cache_read_tokens are accumulated

2. Accumulation is per-run, not per-LLM-call:
   - run_input_tokens: Sum across all LLM calls in this execution
   - run_output_tokens: Sum across all LLM calls in this execution
   - run_cache_read_tokens: Sum across all LLM calls in this execution

3. The separate thread-title-generation call is excluded:
   - It's a plain .ainvoke() outside the graph
   - It never appears in the astream_events loop
   - It's excluded from usage tracking automatically

USAGE METRICS
-------------
Each StreamRecord stores the following usage fields:
- input_tokens: Total input tokens across all LLM calls
- cache_read_tokens: Total cache-read tokens (prompt caching)
- output_tokens: Total output tokens across all LLM calls
- total_tokens: Computed as input_tokens + output_tokens (not stored, derived in API)

These fields are NULL until at least one LLM call completes. Failed runs may still have usage data if the LLM call succeeded but later steps failed.

LLM SOURCE TRACKING
-------------------
Each StreamRecord also stores the source of the LLM credentials:
- llm_source: "default" (platform key) or "byok" (user key)
- llm_provider: Provider name (e.g., "openai", "anthropic")
- llm_model: Model name (e.g., "gpt-4o", "claude-3-5-sonnet-20241022")

This is set once per run in resolve_llm_for_agent() and persisted to the StreamRecord, enabling clear separation of platform vs. user costs.

COST CALCULATION
----------------
Cost is calculated using LiteLLM's standardized pricing (_compute_cost_usd in chat_service.py):

1. litellm.cost_per_token() is called with:
   - model: The exact model string
   - prompt_tokens: input_tokens
   - completion_tokens: output_tokens
   - cache_read_input_tokens: cache_read_tokens

2. Returns prompt_cost and completion_cost based on LiteLLM's pricing database

3. Total cost = prompt_cost + completion_cost, rounded to 6 decimal places

4. If pricing is unknown for the model:
   - Exception is caught and logged as warning
   - Returns None (cost_usd stays NULL in database)
   - Token counts are still recorded

5. Environment variable LITELLM_LOCAL_MODEL_COST_MAP="True":
   - Forces LiteLLM to use only the bundled local pricing file
   - Prevents network fetches for pricing data
   - Avoids latency and ensures deterministic cost calculation

COST PERSISTENCE
----------------
Cost is persisted to StreamRecord.cost_usd:
- NULL if pricing is unknown or no LLM calls completed
- Numeric(12, 6) in database for high precision
- Set at run completion (COMPLETED, CANCELLED, or FAILED)
- Even failed runs may have cost if LLM calls succeeded before failure

PERIODIC FLUSHING
-----------------
Usage data is periodically flushed to the database during execution:
- Every TOKEN_FLUSH_INTERVAL (50) tokens, a flush occurs
- This provides crash-recovery for long-running generations
- If the server crashes, partial usage is still captured
- The final completion flush overwrites with final totals

The flush includes:
- partial_content: Current response content
- reasoning: Current reasoning steps (including partial in-progress blocks)
- input_tokens, cache_read_tokens, output_tokens: Current totals
- llm_source, llm_provider, llm_model: LLM identification
- total_chunks: Current chunk count

PLATFORM VS BYOK COST DISTINCTION
---------------------------------
The key distinction between platform and BYOK costs:

Platform costs (llm_source="default"):
- Paid for by ThinkLoop's platform API keys
- Tracked so the platform can monitor overall consumption
- Users can see which runs used platform resources
- No direct cost to the user (platform's expense)

BYOK costs (llm_source="byok"):
- Paid for by the user's own API keys
- Tracked so users can monitor their own provider consumption
- Costs are charged to the user's provider account directly
- ThinkLoop only tracks usage, doesn't handle billing

This separation is critical for:
- Users understanding their own API key usage
- Platform monitoring its own costs
- Clear attribution of which runs consumed which resources

USAGE AGGREGATION AND QUERIES
------------------------------
Usage data is exposed through multiple APIs:

1. Summary (GET /usage/summary):
   - total_spent_usd: Sum of cost_usd across all runs
   - total_threads: Count of distinct threads
   - total_runs: Count of StreamRecords
   - total_agents: Count of top-level agents
   - Uses LEFT JOIN to count threads with zero runs
   - Uses COUNT(DISTINCT) to avoid multi-run thread double-counting

2. List runs (GET /usage/runs):
   - Paginated list of individual runs
   - Filterable by agent, date range, provider, model, status
   - Shows per-run token counts and cost
   - Ordered newest-first
   - Includes llm_source for platform/BYOK distinction

3. Download runs (GET /usage/runs/download):
   - CSV export of filtered runs
   - Same filters as list_runs
   - Capped at MAX_EXPORT_ROWS (50,000) to prevent memory issues
   - Returns was_truncated flag if cap hit
   - Excludes internal IDs (stream_id, thread_id, agent_id)

4. Per-thread reasoning (GET /threads/{id}/messages):
   - Each assistant message includes reasoning from associated StreamRecord
   - Shows the reasoning trace alongside the final response
   - Enables users to understand what the agent did

USAGE IN FAILED RUNS
--------------------
Usage is captured even when runs fail:
- If LLM calls succeed but later steps fail, token usage is still recorded
- Cost is calculated for whatever tokens were consumed
- This provides accurate accounting even for incomplete executions
- Status is FAILED but usage data is present

Examples:
- Tool execution failure after LLM response: tokens counted
- Title generation failure after main response: tokens counted
- Synthesizer failure after sub-agents complete: all tokens counted
- Cancellation mid-stream: tokens up to cancellation point counted

USAGE IN CANCELLED RUNS
-----------------------
Cancelled runs also capture usage:
- Tokens consumed before cancellation are recorded
- Cost is calculated for partial usage
- Reasoning steps up to cancellation are preserved
- Status is CANCELLED but usage data is present
- This prevents "free" usage via cancellation

USAGE IN SCHEDULED RUNS
-----------------------
Scheduled runs are tracked identically to manual runs:
- Each scheduled execution creates a new Thread and StreamRecord
- Usage is captured per execution, not per schedule
- ScheduleRun links to the StreamRecord for reconciliation
- llm_source is correctly set based on the agent's model selection
- Scheduler reconciliation pass updates ScheduleRun.status based on StreamRecord

USAGE IN SUB-AGENT CALLS
-------------------------
Sub-agent usage is folded into the parent run:
- All LLM calls (parent + sub-agents + synthesizer) accumulate to the same totals
- There is no separate usage tracking per sub-agent
- The user sees one total per parent agent execution
- This simplifies the mental model: one run = one total

PRICING DATA SOURCE
------------------
Pricing data comes from LiteLLM:
- Bundled local pricing file (litellm/model_prices.json)
- Forced local via LITELLM_LOCAL_MODEL_COST_MAP="True"
- No network fetches for pricing at runtime
- Deterministic cost calculation for a given litellm version
- Platform can update litellm version to get new model pricing

If a model is not in LiteLLM's pricing database:
- cost_usd remains NULL
- Token counts are still recorded
- User can see usage but not cost
- Warning is logged for debugging

MISSING PRICING HANDLING
-------------------------
When pricing is unavailable:
- _compute_cost_usd returns None
- cost_usd stays NULL in database
- No error is raised to the user
- Token counts are still accurate
- This is better than showing incorrect costs

Common causes:
- New model not yet in LiteLLM's database
- Custom/fine-tuned model names
- Provider not yet supported by LiteLLM

EDGE CASES AND FAILURE SCENARIOS
----------------------------------
1. **LiteLLM pricing lookup failure**: Logged as warning, cost_usd remains NULL

2. **Model name mismatch**: If the model string doesn't match LiteLLM's database, cost is unavailable

3. **Cache read tokens not supported**: Some providers/models don't report cache_read_tokens; treated as 0

4. **Run fails before any LLM call**: All usage fields remain NULL

5. **Run cancelled immediately**: Minimal usage recorded, cost calculated for partial usage

6. **Concurrent runs**: Each run has independent StreamRecord and usage tracking

7. **Sub-agent timeout**: Tokens consumed before timeout are still counted

8. **Provider returns malformed usage_metadata**: Treated as 0, logged for debugging

9. **Platform default model changed**: Existing runs keep their original llm_model value

10. **BYOK key rotated mid-run**: Run continues with the key it started with; next run uses new key

SECURITY AND PRIVACY
--------------------
- Usage data is scoped to user_id via Thread.user_id
- Users can only see their own usage
- No cross-user usage aggregation
- Internal IDs are excluded from CSV exports
- Cost data is read-only for users (no modification API)

4. REASONING WORKFLOW
================================================================

OVERVIEW
--------
The reasoning workflow captures and exposes the agent's step-by-step thinking process during execution. This includes the agent's internal reasoning, tool calls, tool results, dispatch decisions, and sub-agent execution. The reasoning trace provides transparency into how the agent arrived at its final response.

REASONING INSTRUCTION
--------------------
Every agent (parent and sub-agent) receives reasoning instruction in its system prompt:

The REASONING_INSTRUCTION (constants.py) requires:
1. Every response must begin with a <reasoning> block as text content
2. No preamble, greeting, or narration before the reasoning block
3. The block contains a concise thinking trace grounded in actual execution context
4. The block must be closed with </reasoning> immediately before tool calls or final answer
5. Specific rules about ambiguous identifiers, repeated failures, and final-answer reasoning

This instruction is injected into every agent's prompt at graph build time, ensuring consistent reasoning behavior across all agents.

REASONING ENABLEMENT
--------------------
Reasoning can be toggled per execution:
- enable_thinking flag is set in the initial graph input
- Derived from User.thinking_enabled (user preference)
- Passed through the graph state to all nodes
- Controls whether reasoning instruction is included in the prompt

Two prompt variants are precomputed at graph build time:
- agent_prompt_with_reasoning: Includes REASONING_INSTRUCTION
- agent_prompt_without_reasoning: Excludes REASONING_INSTRUCTION

The agent node selects the appropriate variant based on state["enable_thinking"] at runtime, avoiding graph rebuilds when the toggle changes.

REASONING TOKEN STREAM SPLITTING
--------------------------------
As tokens stream from the LLM, they are split into reasoning and content channels:

The ReasoningSplitter (utils/reasoning_splitter.py):
- Maintains state per LLM run_id (one instance per LLM call)
- Feeds raw token strings from on_chat_model_stream events
- Detects <reasoning> and </reasoning> tags in the stream
- Routes tokens to either "reasoning" or "content" channel
- Emits SplitChunk objects with channel, text, and event type

SplitChunk types:
- channel: "reasoning" or "content"
- text: The actual token content
- event: "start" (reasoning block opened), "end" (reasoning block closed), or None
- truncated: True if the block was force-closed due to length

Safety mechanisms:
- Force-close after REASONING_FORCE_CLOSE_AFTER_TOKENS (1200) tokens
- Prevents runaway reasoning blocks that never close
- Truncated flag indicates forced closure
- Sanitization of literal tags in untrusted text (tool output, scraped content)

REASONING EVENTS
----------------
During execution, reasoning-related SSE events are emitted:

1. reasoning_start:
   - Emitted when <reasoning> tag is detected
   - Includes agent name (which agent is reasoning)
   - Marks the beginning of a reasoning block

2. reasoning_token:
   - Emitted for each token within a reasoning block
   - Includes the token content and agent name
   - Streams reasoning content in real-time

3. reasoning_end:
   - Emitted when </reasoning> tag is detected
   - Includes agent name and truncated flag
   - Marks the end of a reasoning block

4. dispatch_decision:
   - Emitted when parent agent decides to delegate to sub-agents
   - Includes target sub-agent name and reasoning
   - Shows why delegation was chosen

5. tool_start / tool_end:
   - Emitted for each tool execution
   - Includes tool name, agent name, and (for end) output
   - Shows what tools were called and what they returned

6. denied_tool_calls:
   - Emitted for tools that were denied or skipped
   - Includes tool name, input, and denial reason
   - Shows what tools were not executed and why

REASONING STEP STRUCTURE
-------------------------
Reasoning steps are stored in a structured format in StreamRecord.reasoning:

Each step has:
- agent: Which agent generated this step (parent or sub-agent name)
- step: Step type ("thought", "tool_call", "dispatch_decision")
- content: The actual reasoning content (for "thought")
- tool_name: Tool name (for "tool_call")
- input: Serialized tool arguments (for "tool_call")
- output: Tool result (for "tool_call")
- duration_ms: Time taken for this step (for "thought" and "tool_call")
- truncated: True if step was cut off (for "thought")
- partial: True if this is an in-progress partial step (for periodic flush)

The reasoning field stores JSON: {"steps": [...]}.

REASONING CAPTURE PROCESS
--------------------------
Reasoning is captured during the astream_events loop in _run_generation:

1. For each on_chat_model_stream event:
   - Token content is fed to the appropriate ReasoningSplitter (keyed by run_id)
   - SplitChunk objects are returned
   - reasoning_start/reasoning_token/reasoning_end events are emitted via SSE
   - Reasoning content is accumulated in reasoning_buffers[run_id]

2. When reasoning_end is emitted:
   - The accumulated content is finalized
   - A reasoning step is created with agent, step="thought", content, duration_ms
   - The step is appended to reasoning_steps list
   - The buffer is cleared

3. For tool calls (on_tool_start/on_tool_end):
   - Tool name, input, output, and duration are captured
   - A reasoning step is created with step="tool_call"
   - The step is appended to reasoning_steps list

4. For dispatch decisions (on_chain_end from agent node):
   - Dispatch decisions are extracted from the node output
   - A reasoning step is created with step="dispatch_decision"
   - The step is appended to reasoning_steps list

5. Periodic flushing (every 50 tokens):
   - Current reasoning_steps are persisted to StreamRecord.reasoning
   - In-progress reasoning blocks are included as partial steps
   - This provides crash-recovery for long-running generations

6. Final completion:
   - All reasoning steps are persisted as JSON
   - StreamRecord.reasoning is finalized
   - The final assistant message is created

REASONING IN SUB-AGENTS
-------------------------
Sub-agents have their own reasoning traces:
- Each sub-agent has its own ReasoningSplitter instance
- Sub-agent reasoning is tagged with the sub-agent's name
- Sub-agent reasoning steps are included in the parent run's reasoning trace
- The synthesizer sees all sub-agent reasoning in the conversation history

Sub-agent reasoning is distinguished by:
- agent field: The sub-agent's node name (e.g., "web_research_agent")
- Separate reasoning_start/reasoning_token/reasoning_end events per sub-agent
- Independent reasoning steps in the final trace

REASONING IN SYNTHESIZER
-------------------------
The synthesizer does not emit separate reasoning events:
- Its job is to produce the final user-visible response
- Its LLM call is not split for reasoning (splitter_is_final=false for synthesizer)
- Its tokens go directly to the final content channel
- No reasoning steps are recorded for the synthesizer itself

The synthesizer receives:
- All parent agent reasoning in the conversation history
- All sub-agent reasoning in the conversation history
- All tool results in the conversation history
- It synthesizes these into a coherent final answer

REASONING WITH TOOL APPROVALS
-----------------------------
When tool approval is required:
- Reasoning generated before the approval is persisted
- The stream pauses with status AWAITING_APPROVAL
- Partial reasoning is saved in StreamRecord.reasoning
- Upon resume, reasoning continues and accumulates
- The final reasoning trace includes both pre- and post-approval reasoning

The approval pause does not lose reasoning:
- Reasoning steps before the pause are persisted
- Reasoning buffers are seeded with prior content on resume
- Token usage accumulates across the pause boundary
- The final trace is seamless

REASONING IN CANCELLED RUNS
----------------------------
When a run is cancelled:
- Open reasoning splitters are flushed to force-close blocks
- Partial reasoning steps are created with truncated=True
- All reasoning steps up to cancellation are persisted
- The final trace shows where execution stopped
- Token usage up to cancellation is recorded

Cancellation handling:
- ReasoningSplitter.flush(generation_ended_cleanly=False) is called
- Any pending reasoning content is emitted
- Open blocks are marked as truncated
- The trace is complete up to the cancellation point

REASONING IN FAILED RUNS
-------------------------
When a run fails:
- Reasoning steps up to the failure are persisted
- The failure does not erase already-captured reasoning
- Token usage up to failure is recorded
- The trace shows what happened before the failure
- Error information is in StreamRecord.error_message

REASONING EXPOSURE TO USERS
---------------------------
Users can access reasoning through:

1. Live SSE stream:
   - reasoning_start/reasoning_token/reasoning_end events in real-time
   - Shows reasoning as it's generated
   - Includes agent names to distinguish parent vs sub-agents

2. Message history API (GET /threads/{id}/messages):
   - Each assistant message includes a reasoning field
   - Contains the full reasoning trace as a structured object
   - Can be displayed in the UI as a collapsible trace

3. Stream status API (GET /streams/{id}/status):
   - Includes reasoning for in-progress or completed streams
   - Useful for reconnecting clients to recover reasoning

REASONING STORAGE
-----------------
Reasoning is stored in StreamRecord.reasoning:
- JSON field containing {"steps": [...]}
- Each step is a structured object with agent, step type, content, etc.
- NULL if no reasoning was captured (e.g., thinking disabled)
- Persisted at completion and during periodic flushes

The reasoning field is separate from Message.content:
- Message.content is the final user-visible response
- StreamRecord.reasoning is the internal thinking trace
- This separation keeps the conversation clean while preserving transparency

REASONING DISABLED
------------------
When a user disables thinking (User.thinking_enabled=False):
- enable_thinking is set to False in the graph input
- The agent node uses agent_prompt_without_reasoning
- No <reasoning> instruction is in the prompt
- The LLM does not emit reasoning tags
- No reasoning events are emitted
- StreamRecord.reasoning remains NULL

This is a user preference for a cleaner, faster experience without the reasoning trace.

REASONING SANITIZATION
----------------------
Untrusted text (tool output, scraped content) is sanitized:
- sanitize_for_reasoning_tags() escapes literal <reasoning> tags
- Prevents injected tags from hijacking the splitter
- Applied to all tool results before they enter the LLM context
- Ensures the reasoning splitter only sees genuine LLM-generated tags

EDGE CASES AND FAILURE SCENARIOS
----------------------------------
1. **LLM never emits </reasoning>**: Force-close after 1200 tokens, marked as truncated

2. **Malformed reasoning tags**: Splitter handles partial tags gracefully with lookahead buffer

3. **Reasoning tags in tool output**: Sanitized to prevent injection attacks

4. **Cancellation during reasoning block**: Flush forces close, marked as truncated

5. **Network error during reasoning**: Partial reasoning persisted, error recorded

6. **Sub-agent timeout**: Sub-agent reasoning up to timeout is captured

7. **Multiple reasoning blocks in one response**: Each block is captured separately

8. **Empty reasoning block**: Still captured as a step with empty content

9. **Reasoning disabled mid-run**: Not possible - flag is set per execution, not changed during

10. **Very long reasoning**: Periodic flushes prevent memory issues, final trace is complete


================================================================
5. IN-MEMORY GRAPH AND MCP TOOL CACHING
================================================================

OVERVIEW
--------
ThinkLoop caches compiled LangGraph agent graphs and MCP tool configurations in memory to avoid repeated database queries, MCP server connections, and graph compilation overhead. This caching is critical for performance, especially at scale with multiple users, agents, sub-agents, and concurrent requests.

WHAT IS CACHED
--------------
Two main things are cached in memory:

1. Compiled LangGraph agent graphs (_graph_cache):
   - Key: (agent_id, llm_model_id or "default")
   - Value: Compiled StateGraph runnable
   - Bounded LRU cache with max size GRAPH_CACHE_MAX_SIZE (100)
   - Includes parent agent graph, sub-agent nodes, tools node, synthesizer

2. MCP tool registry (_agent_tool_registry):
   - Key: agent_id (parent or sub-agent)
   - Value: List of LangChain tool objects
   - Unbounded (but naturally limited by number of agents/tools)
   - Includes tool metadata (mcp_connection_id, tool_id)

3. Tool permissions map (_agent_tool_permissions):
   - Key: agent_id
   - Value: {tool_name: requires_approval} mapping
   - Unbounded (but naturally limited)
   - Used by the tools node to check approval requirements

4. Active MCP clients (_active_mcp_clients):
   - Key: connection_id
   - Value: MultiServerMCPClient instance
   - Keeps async sessions alive for tool execution
   - Prevents garbage collection of connections

ARCHITECTURAL REASONING FOR CACHING
-----------------------------------

Without caching, each request would require:

1. Database queries:
   - Fetch Agent record
   - Fetch all sub-agents
   - Fetch all AgentTool assignments
   - Fetch all MCPTool records
   - Fetch all MCPConnection records
   - Fetch ProviderModel for LLM resolution
   - Fetch LlmCredential for BYOK keys

2. MCP server connections:
   - Connect to each MCP server
   - Authenticate with API keys
   - Discover available tools via MCP protocol
   - Initialize tool objects
   - This involves network round-trips to each MCP server

3. Graph compilation:
   - Build parent agent node with system prompt
   - Build tools node with permission checks
   - Build synthesizer node
   - Build each sub-agent node with its own ReAct loop
   - Add all nodes to StateGraph
   - Add edges (START → agent, agent ⇄ tools, agent → synthesizer, etc.)
   - Compile the graph with checkpointer
   - This is CPU-intensive and involves LangGraph internal processing

4. LLM instance construction:
   - Resolve provider and model
   - Decrypt API key (if BYOK)
   - Build LangChain chat model instance
   - Configure HTTP client with connection pooling

All of this would happen for EVERY request, leading to:
- High latency (database queries + MCP connections + graph compilation)
- High database load (repeated queries for same data)
- High network load (repeated MCP server connections)
- High CPU usage (repeated graph compilation)
- Poor scalability under concurrent load

With caching, a typical request becomes:

1. Check cache for compiled graph (O(1) lookup)
2. If cache hit, use cached graph directly
3. If cache miss, build and cache for future requests
4. Tool registry is already populated from startup or prior requests
5. MCP clients are already connected and ready
6. LLM instance is built only once per agent execution (not cached, but fast)

This reduces per-request overhead to:
- O(1) cache lookup
- Minimal database queries (only for request-specific data)
- No MCP server connections (already connected)
- No graph compilation (already compiled)
- Much lower latency and resource usage

PERFORMANCE IMPACT
------------------

Database overhead without caching:
- 10-20 queries per request (agents, tools, connections, credentials)
- Each query adds ~1-10ms latency
- Total database overhead: ~50-200ms per request
- Under 100 concurrent requests: 5-20s of database time per second

MCP connection overhead without caching:
- 1-3 MCP server connections per request
- Each connection: ~100-500ms (TCP handshake + authentication + tool discovery)
- Total MCP overhead: ~100-1500ms per request
- Under 100 concurrent requests: 10-150s of MCP connection time per second

Graph compilation overhead without caching:
- ~50-200ms per graph compilation
- Includes node creation, edge addition, LangGraph internal processing
- Total compilation overhead: ~50-200ms per request
- Under 100 concurrent requests: 5-20s of CPU time per second

Total overhead without caching: ~200-1900ms per request
With caching: ~5-20ms per request (cache lookup + minimal queries)

This is a 10-100x improvement in per-request latency.

RESOURCE USAGE IMPACT
---------------------

Without caching:
- Database: High query rate, connection pool pressure
- Network: Repeated MCP server connections
- CPU: Repeated graph compilation
- Memory: Low (no caching), but high churn

With caching:
- Database: Low query rate (cache hits avoid most queries)
- Network: One-time MCP connections per server
- CPU: One-time graph compilation per agent
- Memory: Higher (cache storage), but stable

The trade-off is memory for performance - a classic caching trade-off that heavily favors caching in this context.

CACHE LIFECYCLE
---------------

Graph cache (_graph_cache):
- Built on first request for an agent
- Reused for subsequent requests for the same agent
- Evicted when LRU limit is reached (GRAPH_CACHE_MAX_SIZE = 100)
- Explicitly invalidated on:
  - Agent update (system prompt, sub-agents changed)
  - Agent deletion
  - LLM credential rotation (for agents using that provider)
  - Tool permission changes (for agents using that tool)
  - MCP connection changes (for agents using tools from that connection)

Tool registry (_agent_tool_registry):
- Built at startup for all agents (build_agent_tool_registry)
- Updated incrementally on:
  - New agent creation
  - Tool assignment changes
  - MCP connection refresh
  - Tool permission changes
- Explicitly invalidated on:
  - Agent deletion
  - MCP connection deletion
  - MCP tool blocking

MCP clients (_active_mcp_clients):
- Created when first connecting to an MCP server
- Kept alive for the lifetime of the server process
- Removed on:
  - MCP connection deletion
  - MCP connection disconnect
  - Server restart

CACHE INVALIDATION TRIGGERS
----------------------------

1. Agent update:
   - System prompt changed → invalidate graph cache
   - Sub-agents added/removed → invalidate graph cache
   - Sub-agent prompts changed → invalidate graph cache
   - Tool assignments changed → update tool registry + invalidate graph cache

2. Agent deletion:
   - Remove from tool registry
   - Invalidate graph cache
   - Remove from parent's sub-agent list (invalidate parent's cache)

3. LLM credential upsert/delete:
   - Invalidate graph cache for all agents using that provider
   - No tool registry impact (LLM choice is separate from tools)

4. Tool permission change:
   - Update tool registry (permissions map)
   - Invalidate graph cache for all agents using that tool
   - If blocking: remove tool from registries entirely

5. MCP connection refresh:
   - Re-sync tools from server
   - Update tool registry with fresh tool objects
   - Invalidate graph cache for affected agents

6. MCP connection delete/disconnect:
   - Evict connection's tools from registries
   - Remove MCP client
   - Invalidate graph cache for affected agents

7. MCP tool blocking:
   - Remove tool from all agent registries
   - Invalidate graph cache for affected agents

POTENTIAL DISADVANTAGES OF CACHING
-----------------------------------

1. Stale data:
   - If cache invalidation is missed, stale data is served
   - Mitigation: Comprehensive invalidation triggers
   - Risk: Medium (mitigated by thorough invalidation logic)

2. Memory usage:
   - Caches consume memory that grows with number of agents/tools
   - Mitigation: LRU eviction for graph cache (bounded)
   - Risk: Tool registry is unbounded (but naturally limited)

3. Multi-worker/multi-instance consistency:
   - Each worker process has its own cache
   - Changes in one worker don't immediately reflect in others
   - Mitigation: Cache invalidation is per-worker
   - Risk: Short-lived inconsistency (acceptable for this use case)

4. Cache warm-up time:
   - After server restart, caches are empty
   - First requests pay the compilation cost
   - Mitigation: build_agent_tool_registry at startup
   - Risk: Temporary latency spike after restart

5. Complexity:
   - Cache invalidation logic must be comprehensive
   - Bugs can lead to stale data or unnecessary cache misses
   - Mitigation: Clear invalidation triggers, testing
   - Risk: Medium (mitigated by code review and testing)

REAL-WORLD EXAMPLE
------------------

Without caching:
```
Request → Fetch Agent (DB) → Fetch Sub-agents (DB) → Fetch Tools (DB) 
→ Fetch MCP Connections (DB) → Connect to MCP Server 1 (network) 
→ Connect to MCP Server 2 (network) → Discover Tools (MCP protocol) 
→ Initialize Tool Objects → Build Agent Node → Build Tools Node 
→ Build Sub-agent Nodes → Build Synthesizer Node → Add Edges 
→ Compile Graph → Execute Agent
```

Time breakdown:
- Database queries: 50-200ms
- MCP connections: 100-1500ms
- Graph compilation: 50-200ms
- Total: 200-1900ms before agent execution even begins

With caching:
```
Request → Retrieve Cached Graph/Tools → Validate Dynamic State (minimal DB) 
→ Execute Agent
```

Time breakdown:
- Cache lookup: <1ms
- Minimal DB queries (user, thread, message): 5-20ms
- Total: 5-20ms before agent execution

SCALING CONSIDERATIONS
-----------------------

At scale with:
- 1000 users
- 5000 agents (5 per user average)
- 20000 tool assignments (4 per agent average)
- 100 MCP connections (0.1 per user average)
- 100 concurrent requests

Without caching:
- 100 requests × 200ms average = 20s of overhead per second
- Database: 1000-2000 queries per second
- MCP connections: 100-300 connections per second
- CPU: 5-20s of graph compilation per second
- System would quickly become overloaded

With caching:
- 100 requests × 10ms average = 1s of overhead per second
- Database: 100-200 queries per second (cache hits avoid most)
- MCP connections: 0 (already connected at startup)
- CPU: 0 (graphs already compiled)
- System scales easily within normal capacity

The difference becomes more pronounced as concurrency increases, making caching essential for production scalability.

CACHE IN MULTI-WORKER DEPLOYMENTS
----------------------------------

In a multi-worker deployment (e.g., Gunicorn with multiple workers):
- Each worker has its own in-memory cache
- Cache invalidation happens per-worker
- Short-lived inconsistency is possible:
  - Worker A invalidates cache after agent update
  - Worker B still has old cached graph for a few seconds
  - Next request to Worker B uses stale graph until its cache is invalidated or evicted

This is acceptable because:
- Inconsistency is short-lived (seconds)
- The stale graph is still functional (just outdated)
- Users rarely make changes during active conversations
- The alternative (no caching) is far worse for performance

If strict consistency is required, a distributed cache (Redis) could be used, but this adds complexity and latency. The current design prioritizes performance over strict consistency for this use case.

STARTUP CACHE POPULATION
-------------------------

At server startup (main.py lifespan):
1. build_agent_tool_registry() is called
2. All active MCPConnections are fetched
3. All active Agents are fetched
4. All AgentTool assignments are fetched
5. All MCPTool records are fetched
6. MCP servers are connected and tools are discovered
7. Tool registry is populated for all agents
8. Graph cache is empty (populated on-demand)

This ensures:
- MCP connections are established before handling requests
- Tool registry is warm for all agents
- First requests still benefit from tool registry caching
- Graph cache warms up naturally as agents are used

CONCLUSION
----------

In-memory caching of graphs and MCP tools is essential for ThinkLoop's performance and scalability. The architectural benefits far outweigh the potential disadvantages, and the comprehensive invalidation logic ensures data stays reasonably consistent. The real-world performance improvement (10-100x latency reduction) makes caching a critical optimization for production deployments.
